# Product Requirements Document (PRD)

## 1. Overview

| Field | Value |
|---|---|
| **Product Name** | agent-sentinel — Type-Safe Agent Policy Sentinel (Haskell) |
| **Feature ID** | 001 |
| **Author** | PM Agent (on behalf of Platform/Security Engineering) |
| **Date** | 2026-06-08 |
| **Version** | 1.1 (Market context + agent-sentinel taxonomy) |

**One-line summary:** A thin, strongly-typed Haskell interception layer (`Sentinel.*`) that sits between an AI agent and an LLM, enforcing composable policies on every request and response — so that whole classes of policy bugs (an un-applied policy, leaked un-redacted PII, an unchecked prompt reaching a model) are made unrepresentable or impossible to bypass.

---

## 2. Problem Statement

Teams deploying AI agents in regulated domains (e.g. adtech) must control exactly what their agents send **to** an LLM and what they accept **back** from it. Today this is typically implemented as ad-hoc, imperative "guard" code — or by bolting on runtime policy engines (OPA, Cedar) that the host must remember to call on every path.

This approach fails in predictable, dangerous ways:
- A developer **forgets to call** the policy check on a new code path → ungoverned prompt reaches the model.
- PII or protected-class attributes are **redacted in one path but not another**.
- A raw model response is **consumed before** brand-safety checks run.
- Policy logic and "send to model" logic are separable, so the compiler permits bypass — even when a Cedar or Rego policy exists elsewhere in the stack.

These are not exotic edge cases — they are the **default failure mode** of policy enforcement written in dynamically-typed or loosely-typed code (or in statically-typed code that treats the policy engine as an optional runtime call), where "did we enforce the policy?" is a runtime question rather than a compile-time guarantee. See §4 for how incumbent policy languages address (or do not address) this gap.

**Who has this problem:** Platform/security engineers and ML-platform teams responsible for the compliance and safety posture of AI agents that call LLMs, especially where regulators care about PII handling, protected-class targeting, brand safety, and disallowed claims.

---

## 3. Security / Confidence Value Proposition

The core differentiator is **confidence derived from the type system**, not features.

By modeling enforcement in Haskell (`Sentinel.*`), we make the dangerous states *unrepresentable*:
- A request cannot be sent downstream to the model unless it is wrapped in a type that proves it has passed enforcement ("no-bypass").
- A model response cannot be consumed by the agent unless it has passed response-side enforcement.
- Policy decisions and violations are **explicit data**, returned from a total pipeline — not exceptions that a caller can silently swallow.
- Inputs are **parsed into precise domain types** at the boundary (parse, don't validate), so downstream code never re-checks invariants the type already guarantees.

The product's promise: *if it compiles, the sentinel ran.*

## 4. Market Context — Type-Safe Policy Languages

Policy enforcement is not a greenfield problem. Teams already choose among several **policy-as-code** languages and engines when they need allow/deny, redaction, or compliance guarantees. Most of those tools target **authorization** (who can do what) or **infrastructure admission** (what config may deploy). **agent-sentinel** targets a different, newer surface: **agent↔LLM traffic** — intercepting prompts and completions with compile-time proof that enforcement cannot be skipped.

This section maps the existing market, classifies how each option achieves (or does not achieve) type safety, and positions agent-sentinel relative to incumbents.

### 4.1 How the market segments

| Segment | Typical problem | Representative tools | Primary safety mechanism |
|---|---|---|---|
| **Authorization (authz)** | Can principal *P* perform action *A* on resource *R*? | Cedar, Rego/OPA, OpenFGA, Casbin, Cerbos | Declarative rules + runtime evaluator; Cedar adds schema validation and SMT analysis |
| **Infrastructure / admission** | Is this deploy/config/plan allowed? | Rego/OPA, CEL + Kubernetes VAP, Terraform Sentinel | Predicate evaluation at gate; CEL is statically typed and non-Turing-complete |
| **Configuration constraints** | Is this data structurally valid and consistent? | CUE, JSON Schema | Unification / schema validation at load time |
| **Host-language enforcement** | Can illegal states be ruled out in application code? | Haskell/Idris eDSLs, Liquid Haskell refinements | Compiler + phantom types; strongest *structural* guarantees |
| **Agent↔LLM interception** *(this product)* | Was every prompt/completion governed before it crossed the model boundary? | **agent-sentinel** (no direct incumbent) | Phantom `Governed` types; enforcement is the only mint of checked values |

No widely adopted product today combines (a) a **standalone declarative policy DSL**, (b) **formal whole-policy verification** like Cedar, and (c) **compile-time no-bypass** for LLM request/response hops. agent-sentinel deliberately occupies the third column's intersection with the agent-LLM row.

### 4.2 Incumbent policy languages (landscape)

#### Tier A — Strong static typing and/or formal analysis

| Language | Origin / ecosystem | Type-safety & analysis | Strengths | Limitations for agent-LLM use |
|---|---|---|---|---|
| **[Cedar](https://www.cedarpolicy.com/)** | AWS (open source); Verified Permissions, Cognito | Schema-validated policies; Lean-proved semantics; SMT-backed analyzer can prove invariants over entire policy sets | Purpose-built for authz; readable `permit`/`forbid`; analyzable, bounded evaluation | Models principal/action/resource triples — not prompt/completion interception; no compile-time coupling to agent call graph |
| **[CEL](https://github.com/google/cel-spec)** | Google; K8s Validating Admission Policy, Cerbos, Firebase | Statically typed, non-Turing-complete expression language | Fast, safe predicates; good for embedded checks | Expressions only — not a full interception pipeline; host must wire every call site |
| **[CUE](https://cuelang.org/)** | CNCF ecosystem | Strong typing via unification; constraint solving | Excellent for typed policy *data* and config bundles | Not a runtime enforcement engine for live LLM traffic |
| **Formulog** | Research (typed Datalog) | Types on logic-programming rules | Brings types to Datalog family | Academic; not production agent-LLM tooling |
| **Liquid Haskell / refinement types** | Haskell ecosystem | Refinement types prove predicates at compile time | Deep compile-time proofs in host language | Requires expert authors; no standalone policy surface for non-Haskell teams |

#### Tier B — Policy-as-code with partial typing

| Language | Type-safety posture | Strengths | Limitations |
|---|---|---|---|
| **[Rego](https://www.openpolicyagent.org/docs/latest/policy-language/)** (OPA) | Datalog-inspired; JSON Schema on *input*; no full static type system; whole-policy equivalence undecidable | General-purpose; huge ecosystem; K8s, Terraform, API gateways | Expressiveness → unpredictable perf; easy to scatter checks; **no compile-time proof** that agent code called OPA |
| **[OpenFGA DSL](https://openfga.dev/)** | Typed relationship models (ReBAC) | Clear ReBAC semantics; good for permissions graphs | Authorization-centric; no LLM prompt/response lifecycle |
| **Cerbos** | YAML policies + typed CEL conditions | Accessible authoring; ABAC-focused | YAML layer untyped; host must enforce every hop |

#### Tier C — Host-language embedded DSLs (closest architectural cousin)

Policies are Haskell (or other host-language) values composed with combinators — not a separate file format. **agent-sentinel's `Sentinel.Policy` module is in this category.**

Examples elsewhere: Servant's typed APIs, Opaleye's typed SQL, finance DSLs (Marlowe). Safety comes from the **host compiler**, not from a standalone policy validator.

### 4.3 Comparative matrix — agent-sentinel vs. market

| Dimension | Cedar | Rego (OPA) | CEL | agent-sentinel |
|---|---|---|---|---|
| **Primary domain** | Authz (ABAC/RBAC) | General policy-as-code | Typed predicates | Agent↔LLM interception |
| **Policy authoring** | Declarative `.cedar` files | Declarative `.rego` files | Embedded expressions | Haskell combinators (`Sentinel.Policy`) |
| **Standalone DSL** | Yes | Yes | Expression-only | No (eDSL today; declarative surface is out of scope §10) |
| **Schema / type validation** | Strong (entity schema) | Partial (JSON Schema) | Strong (CEL types) | Strong (smart constructors, newtypes) |
| **Whole-policy formal proof** | Yes (SMT analyzer) | No (generally) | Limited | No (property tests + type proofs for structural invariants) |
| **No-bypass guarantee** | Runtime only (engine must be called) | Runtime only | Runtime only | **Compile-time** (`Governed 'Checked` is the only model input) |
| **Request + response interception** | N/A (authz decision) | Possible but not structured for LLM lifecycle | Possible per-check | **First-class** (`enforceRequest` + `enforceResponse`) |
| **Non-Haskell policy authors** | Yes | Yes | Yes (via config) | No (requires Haskell) |
| **Offline deterministic tests** | Yes | Yes | Yes | Yes (mock `ModelBackend`; no Ollama in CI) |

### 4.4 Where agent-sentinel wins

1. **Structural no-bypass** — Competitors assume the host application correctly invokes the policy engine on every path. agent-sentinel makes "call model without enforcement" a **type error**, not a code-review finding.
2. **Symmetric LLM lifecycle** — Policies apply at both outbound (prompt) and inbound (completion) interception points with the same `Governed`/`Stage` model.
3. **Explicit decision algebra** — `Allow` / `Deny` / `Transform` / `Redact` are total sum types; violations are data, not exceptions.
4. **Composable policy values** — `Semigroup` composition with documented semantics (deny absorbing, redactions accumulate) without modifying `Sentinel.Enforce`.

### 4.5 Where agent-sentinel does not compete (and should not)

| Capability | Better served by |
|---|---|
| Enterprise authz at API/resource layer | Cedar, OPA, OpenFGA, Cerbos |
| Org-wide policy distribution / audit UI | OPA bundles, AVP, commercial PDPs |
| Non-engineer policy authoring | Cedar, Rego, Cerbos YAML |
| Proving "no policy grants Admin Delete" over 10k rules | Cedar Analyzer (SMT) |
| Kubernetes / Terraform gatekeeping | OPA, CEL + VAP |

agent-sentinel is **not** a replacement for Cedar or OPA in the authorization control plane. It is a **library primitive** for teams that embed LLM calls in Haskell agents and need compile-time confidence that policy ran on every hop.

### 4.6 Positioning statement

> **agent-sentinel = host-language type safety for agent↔LLM policy enforcement**, analogous to how Servant gives compile-time API safety — whereas **Cedar/Rego = declarative policy languages evaluated at runtime** for authorization and compliance gates.

A plausible future evolution (out of scope for v1, see §10): a **declarative policy surface** (YAML, Cedar-like syntax, or quasiquotes) that **lowers to `Sentinel.Policy`**, combining approachable authoring with the existing no-bypass core.

### 4.7 Implications for product goals

| Market gap | agent-sentinel response | Traces to |
|---|---|---|
| No incumbent enforces LLM interception structurally | `Governed` phantom types + unexported constructors | G1, G3, FR5 |
| Rego/Cedar authors can't get compile-time call-graph guarantees | Enforcement embedded in agent's type signatures | G3, NFR7 |
| Policy engines don't model redact/transform on completions | `Decision` sum type + `enforceResponse` | G2, FR1, FR2 |
| Compliance stakeholders need credible offline proof | Deterministic test suite + property laws (idempotence, deny absorbing, redaction non-leak) | G5, NFR3 |

## 5. Goals & Success Metrics

### 5.1 Goals

| # | Goal |
|---|---|
| G1 | Guarantee that no request reaches the model, and no response reaches the agent, without passing typed enforcement. |
| G2 | Express policies as composable, typed, first-class values (`Sentinel.Policy`). |
| G3 | Eliminate, at compile time, identified classes of policy bugs. |
| G4 | Provide a credible, regulated-domain flagship example (adtech). |
| G5 | Build and run reproducibly on both macOS Intel and Apple Silicon, and be fully testable offline. |

### 5.2 Success Metrics

The headline success framing is **"classes of bugs eliminated by the type system"** — measured by demonstrating that each listed bug class is a *compile error or unrepresentable state*, not a runtime hope.

| Goal | Metric | Target |
|---|---|---|
| G1 | "No-bypass" property: attempts to call the model with an ungoverned value | Does not compile (demonstrated by a documented negative/`should-not-compile` case) |
| G3 | Policy bug classes provably eliminated by types | ≥ 4 classes (forgotten policy application, un-redacted PII leak, unchecked prompt to model, consumed-before-checked response) |
| G2 | Policies are composable typed values combinable without engine changes | New policy added by composition only, zero changes to `Sentinel.Enforce` core |
| G4 | Flagship adtech scenario passes end-to-end | All acceptance criteria in §11 pass against Ollama llama3.2 |
| G5 | Reproducible cross-platform build | `stack build` + `stack test` green on x86_64 **and** aarch64 from the pinned resolver |
| G5 | Offline testability | Full deterministic test suite passes in CI with **no** Ollama present |

> Note: raw latency/throughput performance is explicitly **not** a success metric (see §8).

## 10. Flagship Use Case & Acceptance Scenario — Adtech

**Scenario:** An ad-copy / audience-targeting assistant agent uses an LLM to draft ad copy and suggest targeting. The sentinel engine (`Sentinel.*`) sits between the agent and the model.

**Request-side policy (to the model):**
- PII present in the request (e.g. names, emails, health information) is **redacted** before the prompt is sent.
- A request that **targets protected categories** (race, religion, health, etc.) is **denied** — it never reaches the model.

**Response-side policy (from the model):**
- Generated ad copy is checked against **brand-safety / disallowed-claims** policy; violating content yields a `Deny`/violation rather than being returned to the agent.

**Acceptance criteria:**
1. A request containing PII is transformed so the redacted attributes do not appear in the prompt sent to the model. *(FR1, FR6a)*
2. A request targeting a protected class returns an explicit `Deny` with a violation value and is never sent to the model. *(FR6c, FR4)*
3. Model-generated copy containing a disallowed claim returns an explicit `Deny`/violation and is not surfaced to the agent. *(FR2, FR6b)*
4. The whole flow runs end-to-end against **Ollama llama3.2**, and an equivalent deterministic version runs against the **mocked model boundary** with identical policy outcomes. *(FR7)*

## 11. Scope & Boundaries

### In Scope
- The typed sentinel/interception layer (`Sentinel.Enforce`, `Sentinel.Policy`, etc.) (FR1–FR7).
- The adtech policy bundle and example agent wiring sufficient to demonstrate the flagship scenario.
- Ollama (llama3.2) integration **and** a deterministic mock model boundary.
- Cross-platform reproducible build on the pinned resolver.

### Out of Scope (Non-Goals)
- **NOT a full agent framework** — no planning, tool-use orchestration, memory, or multi-agent coordination.
- **NOT a model host / inference server** — the product does not serve or run models; Ollama is an external dependency used only for the example.
- No GUI, dashboard, or hosted SaaS control plane.
- No declarative policy DSL beyond typed Haskell combinators (see §4.6 for market rationale); no dynamic/remote policy loading.
- No performance/latency optimization or benchmarking targets.
- No persistence layer, user management, or multi-tenancy.
- No production-grade audit/log shipping pipeline (host app owns logging; engine only returns structured data).

## 12. Assumptions

- **A1** — Feature ID is `001`; PRD is delivered as the single file `docs/001/001-prd.md` per the brief.
- **A2** — Consumers are Haskell-capable platform/ML engineers; the public API can be idiomatic Haskell rather than FFI/multi-language.
- **A3** — Ollama with `llama3.2` is available locally for end-to-end runs; CI relies solely on the mocked boundary.
- **A4** — Policy lists for PII / protected classes / disallowed claims can be represented as typed, in-code policy values for this scope (no external policy service).
- **A5** — Determinism of policy outcomes is evaluated on the **policy decisions**, not on the (inherently non-deterministic) raw LLM text.
- **A7** — Teams evaluating agent-sentinel against Cedar/OPA understand it complements (not replaces) authorization control planes (§4.5).
- **A6** — `lts-22.43` / GHC 9.6.6 bindists remain available for both x86_64 and aarch64 macOS.

## 13. Risks & Mitigations

| Risk | Impact | Likelihood | Mitigation |
|---|---|---|---|
| Legacy local toolchain (GHC **8.2.2**) lacks features and cross-arch bindists | Build fails / non-reproducible | High (pre-mitigation) | **Pin GHC 9.6.6 via modern stack resolver `lts-22.43`** (NFR2); do not rely on system GHC. |
| Ollama/llama3.2 absent or non-deterministic in CI | Flaky or failing CI | High | Mock the model boundary; CI uses the deterministic suite only (FR7, NFR3). |
| "No-bypass" guarantee is weaker than claimed (a leaky constructor) | Erodes core value prop | Medium | Encapsulate the governed type (no exported constructor); add a documented negative compile case (FR5). |
| Apple Silicon vs Intel build divergence | One arch ships broken | Medium | Pinned resolver with bindists for both arches; build+test on both (NFR1, NFR2). |
| Policy lists treated as the product's "intelligence" rather than the type guarantees | Scope creep into content classification | Medium | Keep policy data minimal/illustrative; the product is the *typed enforcement structure*, not the word lists (NFR4). |
| Scope creep toward a full agent framework | Loses focus, balloons surface area | Medium | Explicit non-goals (§11); minimal surface area (NFR4). |
| Confusion with Cedar/OPA positioning | Wrong buyer expectations; feature creep into authz | Medium | §4 market context; explicit non-compete table (§4.5); stay on LLM interception |
